# Обробка даних функціями

## Потік даних

```
емулятор ──POST──▶ ingest ──▶ черга telemetry ──тригер──▶ process ──▶ PostgreSQL (measurements)
                    │                │                        │
              валідація, 202    до 3 спроб                 перевірка діапазону,
                                      │                    відхилення, перерахунок,
                                      ▼ після 3-ї невдачі   INSERT ON CONFLICT DO NOTHING
                              черга недоставлених
                              (telemetry/$deadletterqueue)
```

## Вибраний дизайн: одна функція з обробниками за типом

Функція `process` (`functions/src/functions/process.js`) має тригер на чергу й для кожного повідомлення викликає `processMeasurement`. Усередині правила розгалужуються за `sensor_type` (`functions/src/lib/processing.js`, об'єкт `RULES`).

**Чому не окрема функція і окрема черга на кожен тип:**

- Типів лише три, а логіка в них однакова за структурою (діапазон, відхилення, збагачення), відрізняються лише межі й функція збагачення. Три функції дублювали б код.
- Одна черга на всіх коштує дешевше й простіше (ціна Service Bus Basic, один тригер, один набір налаштувань).
- Маршрутизація на рівні черги (тема з підписками й фільтрами) потребує тарифу Standard, дорожчого за потреби цієї задачі.

**Що це коштує:** різні типи датчиків масштабуються разом. Якщо один тип надсилатиме на порядок більше повідомлень, він займатиме загальні екземпляри; окремі черги дали б ізоляцію. Для трьох рівноцінних датчиків це не проблема. Якщо типів стане багато або їхня обробка вимагатиме різних ресурсів, правильним кроком буде тема з підписками (кожен тип на власну функцію).

## Що робить обробка для кожного типу

| Тип | Допустимий діапазон | Позначення аномалії | Збагачення (поле `details`) |
|---|---|---|---|
| `temperature` | -50…80 °C | відхилення від попереднього вимірювання понад 5 °C | перерахунок у градуси Фаренгейта `value_f` |
| `humidity` | 0…100 % | відхилення понад 20 п.п. | категорія комфорту: `dry` (< 30), `comfortable`, `humid` (> 60) |
| `light` | 0…100 000 lx | відхилення понад 5 000 lx | категорія `dark`, `dim`, `indoor`, `bright` |

Для кожного повідомлення функція:

1. Перевіряє формат ще раз (захист, якщо повідомлення потрапило в чергу в обхід приймача).
2. Читає попереднє вимірювання цього датчика (`measured_at` менший за поточний).
3. Рахує `deviation = значення - попереднє значення`.
4. Ставить `is_anomaly = true` й причину в `anomaly_reason` (`out_of_range`, `sudden_jump` або обидві через кому), якщо значення поза діапазоном чи різкий стрибок. Такі вимірювання **не відкидаються**: вони зберігаються з позначкою, щоб історія була повною.
5. Записує рядок у базу.

## Ідемпотентність

Черги Service Bus гарантують доставку «щонайменше один раз»: те саме повідомлення може прийти двічі (після збою функції, після закінчення часу блокування). Тому запис ідемпотентний:

- Первинний ключ таблиці `(sensor_id, measured_at)`: одне вимірювання одного датчика в один момент часу може бути записане лише раз.
- Запис виконується як `INSERT … ON CONFLICT (sensor_id, measured_at) DO NOTHING`. Друга доставка не створює дубля й не падає: рядків вставлено 0, функція успішно завершується, повідомлення підтверджується.

Повторне надсилання того самого вимірювання емулятором (наприклад, після таймауту) теж безпечне з тієї ж причини.

## Що відбувається з повідомленням, яке функція не змогла обробити

1. Функція кидає виняток (невідомий тип датчика, зіпсований JSON, помилка бази).
2. Service Bus не підтверджує повідомлення й повертає його в чергу після закінчення блокування (1 хв), збільшуючи лічильник доставок.
3. Спроби повторюються до `max_delivery_count = 3`.
4. Після третьої невдачі повідомлення автоматично переміщується в чергу недоставлених (`telemetry/$deadletterqueue`) разом із причиною. Основна черга при цьому не зупиняється: інші повідомлення обробляються як завжди.

Тимчасові помилки (наприклад, база на мить недоступна) вирішуються повторною спробою, а «отруйні» повідомлення не блокують потік (докладно в `DLQ.md`).
