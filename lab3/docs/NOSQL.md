# Нереляційна база для сирих даних

## Що зроблено

Кожне вимірювання в первинному вигляді (рівно те тіло, яке прийшло від датчика) зберігається в **Azure Cosmos DB** (API NoSQL, режим serverless, `terraform/cosmos.tf`):

| | Значення |
|---|---|
| Акаунт | `cosmos-iot-…`, Switzerland North, serverless (оплата за спожиті RU, без резервування) |
| База / контейнер | `telemetry` / `raw` |
| Ключ розділу (partition key) | `/sensor_id` |
| «Ключ сортування» | `id = measured_at` + `ORDER BY c.measured_at` |

У Cosmos DB немає окремого ключа сортування, як у DynamoDB. Його роль виконують дві речі: `id` документа дорівнює `measured_at` (унікальний у межах розділу, тож пара `sensor_id` + `measured_at` однозначно визначає запис), а діапазонний індекс за замовчуванням дозволяє швидко читати `measured_at` за діапазоном і в порядку спадання.

Запис робить функція `process` (`functions/src/lib/nosql.js`, `saveRaw`) операцією `upsert`, тож повторна доставка повідомлення просто перезаписує той самий документ: ідемпотентність, як і в PostgreSQL.

Запит історії має варіант читання з Cosmos: `GET /api/sensors/{sensor_id}/history?source=nosql&from=…&to=…&limit=…`.

## Як виглядає запит історії

**PostgreSQL** (`functions/src/functions/history.js`):

```sql
SELECT … FROM measurements
WHERE sensor_id = $1 AND measured_at BETWEEN $2 AND $3
ORDER BY measured_at DESC
LIMIT $4
```

Використовує індекс первинного ключа `(sensor_id, measured_at)`.

**Cosmos DB** (`functions/src/lib/nosql.js`):

```sql
SELECT TOP @limit c.sensor_id, c.sensor_type, c["value"], c.unit, c.location, c.measured_at
FROM c
WHERE c.sensor_id = @id AND c.measured_at >= @from AND c.measured_at <= @to
ORDER BY c.measured_at DESC
```

з опцією `partitionKey: sensorId`. Запит іде лише в **один фізичний розділ**, тому коштує кілька RU незалежно від кількості інших датчиків.

## Які запити зручні в одному і дорогі в іншому

| Запит | PostgreSQL | Cosmos DB |
|---|---|---|
| Історія одного датчика за період | швидко (індекс) | швидко й дешево (один розділ) |
| Середня температура по всіх датчиках за годину | один `GROUP BY` | запит через усі розділи (cross-partition), дорогий у RU |
| Об'єднати вимірювання з довідником датчиків (власник, адреса) | `JOIN` | немає `JOIN` між документами: треба дублювати дані або два запити |
| Аномалії за весь період | частковий індекс `WHERE is_anomaly` | сканування всіх розділів |
| Нове поле в повідомленні (наприклад, заряд батареї) | міграція схеми | нічого не міняти: документ без схеми |
| Транзакція між кількома датчиками | звична | лише в межах одного розділу |

## Як масштабується запис при зростанні кількості датчиків

**PostgreSQL:** один сервер приймає всі записи. Більше датчиків означає більше записів на той самий диск і процесор і більше з'єднань від функцій. Масштабування переважно вертикальне (потужніший сервер); горизонтальне (шардінг) доводиться будувати вручну. У цій роботі сервер B1ms (1 ядро) уже в межах ~50 записів/с близький до своїх меж за з'єднаннями.

**Cosmos DB:** записи розподіляються між фізичними розділами за `sensor_id`. Новий датчик це просто новий логічний розділ; коли даних чи навантаження стає більше, служба сама ділить фізичні розділи. Пропускна здатність росте майже лінійно з кількістю датчиків, а з'єднань як таких немає (HTTP-запити до служби). Обмеження: один логічний розділ (один датчик) не може перевищити 20 ГБ і ~10 000 RU/с, тож для «гарячого» датчика ключ довелося б розширити (наприклад, `sensor_id` + день).

## Висновок

Для **потоку телеметрії** (багато датчиків, постійний запис, читання історії одного датчика) краще підходить **нереляційна база з ключем розділу `sensor_id`**: запис масштабується горизонтально без меж за з'єднаннями, а головний запит читає один розділ. Реляційна база варта там, де потрібні аналітичні запити по всіх датчиках, `JOIN` із довідниками й строга схема. Практичний варіант, який і реалізовано тут: сирий потік у NoSQL, а оброблені й агреговані дані в реляційній базі для звітів.
