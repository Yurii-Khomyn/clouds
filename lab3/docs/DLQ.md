# Черга недоставлених повідомлень

## Налаштування

У Service Bus кожна черга має вбудовану підчергу недоставлених повідомлень (`telemetry/$deadletterqueue`). Окремий ресурс створювати не потрібно, налаштовується лише кількість спроб (`terraform/servicebus.tf`):

```hcl
resource "azurerm_servicebus_queue" "telemetry" {
  name               = "telemetry"
  max_delivery_count = 3      # після 3-ї невдалої спроби повідомлення йде в DLQ
  lock_duration      = "PT1M" # скільки повідомлення заблоковане за обробником
}
```

Як це працює:
1. Функція `process` бере повідомлення з блокуванням (peek-lock).
2. Якщо функція кидає виняток, повідомлення повертається в чергу, а лічильник доставок (`deliveryCount`) зростає.
3. Після третьої невдачі Service Bus сам переміщує повідомлення в DLQ з причиною `MaxDeliveryCountExceeded`. Повідомлення не губиться і більше не повторюється.

## Демонстрація

Скрипт `scripts/send-poison.js` кладе в чергу напряму (в обхід валідації приймача) повідомлення з невідомим типом датчика й нечисловим значенням:

```json
{ "sensor_id": "broken-01", "sensor_type": "pressure", "value": "not-a-number", "unit": "hPa", ... }
```

```bash
cd lab3
export SERVICEBUS_CONNECTION=$(cd terraform && terraform output -raw servicebus_connection)
NODE_PATH=functions/node_modules node scripts/send-poison.js   # надіслати
NODE_PATH=functions/node_modules node scripts/dlq.js           # подивитися DLQ
```

Результат (25.11.2026, 11:44 UTC): за кілька секунд повідомлення тричі потрапило до функції, тричі викликало помилку `unsupported sensor_type: pressure` і опинилось у DLQ:

```
dead-letter queue telemetry/$deadletterqueue: 1 message(s)
{
  "messageId": "poison|2026-11-25T11:44:54.158Z",
  "deliveryCount": 3,
  "reason": "MaxDeliveryCountExceeded",
  "description": "Message could not be consumed after 3 delivery attempts.",
  "body": { "sensor_id": "broken-01", "sensor_type": "pressure", "value": "not-a-number", ... }
}
```

Стан черги після цього: `active: 0, dead: 1`.

**Повторна демонстрація під навантаженням.** О 11:52:38 UTC, посеред 5-хвилинного прогону емулятора (11:51:52–11:56:54, ~48 повідомлень/с), у чергу надіслано друге отруйне повідомлення. Через 30 секунд стан черги був `active: 17, dead: 2`: отруйне повідомлення вже в DLQ, а нормальний потік іде (17 повідомлень в обробці це звичайна черга в русі). Після кінця прогону: `active: 0, dead: 2`, а всі 14 606 вимірювань записані в базу. Отже, одне зіпсоване повідомлення не зупинило обробку решти.

## Хто і як має розбирати цю чергу

DLQ це не смітник, а черга інцидентів:

1. **Сповіщення.** Алерт на метрику `DeadletteredMessages > 0` (Azure Monitor) надсилає лист черговому інженеру; без цього DLQ мовчки накопичує дані.
2. **Аналіз.** Інженер дивиться причину (`deadLetterReason`, текст помилки в журналах функції) і тіло повідомлення (як `scripts/dlq.js`).
3. **Рішення для кожного повідомлення:**
   - помилка в коді функції (наприклад, новий тип датчика): виправити функцію, потім **повторно надіслати** повідомлення з DLQ в основну чергу;
   - дані справді зіпсовані (як тут): зберегти для звіту й видалити;
   - тимчасовий збій (база була недоступна довше за всі спроби): повторно надіслати.
4. **Звідки беруться дублі при повторній відправці?** Ніякі: обробка ідемпотентна (первинний ключ `(sensor_id, measured_at)`), тож повторне надсилання безпечне.
