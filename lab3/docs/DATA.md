# Збереження і читання історії

## Схема

Одна таблиця `measurements` для всіх типів датчиків (`functions/src/lib/db.js`):

| Стовпець | Тип | Призначення |
|---|---|---|
| `sensor_id` | text | Датчик |
| `measured_at` | timestamptz | Час вимірювання |
| `sensor_type` | text | Тип датчика |
| `value`, `unit` | double precision, text | Значення й одиниця |
| `lat`, `lon` | double precision | Координати |
| `deviation` | double precision | Відхилення від попереднього вимірювання |
| `is_anomaly`, `anomaly_reason` | boolean, text | Позначка аномалії та причина |
| `details` | jsonb | Поля, специфічні для типу (`value_f`, `comfort`, `category`) |
| `received_at` | timestamptz | Коли запис потрапив у базу |

**Первинний ключ:** `(sensor_id, measured_at)`.

**Індекси:**
- Первинний ключ одразу є індексом для головного запиту «вимірювання датчика за діапазоном часу» (його можна читати у зворотному порядку без сортування).
- `measurements_type_time_idx (sensor_type, measured_at DESC)`: запити за типом.
- `measurements_anomaly_idx (measured_at DESC) WHERE is_anomaly`: частковий індекс лише для аномалій, малий і швидкий.

## Чому одна таблиця, а не окрема на кожен тип

| | Одна таблиця | Таблиця на тип |
|---|---|---|
| Спільні поля (датчик, час, значення, координати) | однакові, зберігаються раз | дублюються в кожній таблиці |
| Новий тип датчика | нічого міняти в схемі, лише правила обробки | нова таблиця й міграція |
| Запит історії за датчиком | один запит | треба знати, до якої таблиці йти |
| Специфічні поля типу | `details` (jsonb) | окремі типізовані стовпці |
| Мінус | специфічні поля менш строго типізовані | багато таблиць, складніші запити по всіх датчиках |

Для телеметрії з однаковою формою (значення + одиниця + час + місце) одна таблиця з `jsonb` для додаткових полів практичніша.

## Запит історії

`GET /api/sensors/{sensor_id}/history?from=…&to=…&limit=…` (з заголовком `x-api-key`)

| Параметр | Опис | За замовчуванням |
|---|---|---|
| `from`, `to` | Межі часу, ISO 8601 | від початку до зараз |
| `limit` | Кількість записів, 1…1000 | 100 |

Відповідь: масив у **зворотному хронологічному порядку** (найновіші першими). Помилкові параметри повертають `400`.

```bash
curl -H "x-api-key: $API_KEY" \
  "$HISTORY_BASE/sensors/temp-kyiv-01/history?from=2026-11-25T12:00:00Z&to=2026-11-25T12:05:00Z&limit=3"
```

```json
[
  {
    "sensor_id": "temp-kyiv-01",
    "sensor_type": "temperature",
    "value": 21.37,
    "unit": "°C",
    "location": { "lat": 50.4501, "lon": 30.5234 },
    "measured_at": "2026-11-25T12:04:59.871Z",
    "deviation": 0.08,
    "is_anomaly": false,
    "anomaly_reason": null,
    "details": { "value_f": 70.47 }
  }
]
```

## Де розташована база

Сервер `psql-iot-spaincentral-…` у регіоні **Spain Central**, хоча функції й черга у Switzerland North. При створенні у `switzerlandnorth` і `austriaeast` Azure повертав `SkuNotAvailable`, у `belgiumcentral` `RegionalAllocationFailed` (нестача потужності), а студентська підписка дозволяє лише 5 регіонів. Затримка між регіонами ~25–30 мс на запит; для асинхронної обробки з черги це не критично. Регіон бази задається змінною `db_location`.

Доступ до бази публічний, але закритий брандмауером: дозволені лише служби Azure (правило `0.0.0.0`, через нього ходять функції) і, на час демонстрації, IP автора (змінна `client_ip`). З'єднання лише через TLS. Функції Flex Consumption можна підключити до приватної мережі (VNet), тоді базу можна зробити повністю приватною, як у лабораторній 1; ціною є складніша мережа і довший холодний старт.

## Як функція підключається до бази

- Рядок підключення (`DATABASE_URL`) і ключ доступу генерує Terraform і передає функції як налаштування застосунку; у репозиторії їх нема.
- Підключення йде через TLS напряму на порт `5432`. Вбудований у Azure PostgreSQL пулер PgBouncer (порт `6432`) був у планах, але Azure відмовив: `PgBouncer isn't supported on servers which are using the Burstable compute tier`. Він доступний лише на тарифах General Purpose і Memory Optimized (у ~8 разів дорожчих), тому вмикається змінною `enable_pgbouncer` у Terraform, а за замовчуванням вимкнений.
- У коді пул `pg` обмежено трьома з'єднаннями на екземпляр функції (`DB_POOL_MAX`), а з'єднання створюється один раз на екземпляр і використовується повторно між викликами.
- Схема створюється самою функцією при першому зверненні (`ensureSchema`) під рекомендаційним блокуванням `pg_advisory_xact_lock`, щоб паралельні екземпляри не створювали таблицю одночасно.

## Чому кількість одночасних з'єднань до бази є обмеженням для serverless-функцій

Кожен запущений екземпляр функції тримає власні з'єднання. Під навантаженням платформа швидко піднімає десятки екземплярів, і кожен відкриває з'єднання. База ж має жорсткий ліміт одночасних з'єднань (для B1ms приблизно 50), а кожне з'єднання PostgreSQL це окремий процес, що споживає пам'ять. Тисяча викликів може означати сотню відкритих з'єднань і помилку `too many connections`. У контейнера з лабораторної 2 було кілька довгоживучих екземплярів із власним пулом, а функцій може бути безліч короткоживучих.

Рішення: (1) **пулер з'єднань** між функціями й базою (PgBouncer: багато клієнтських з'єднань мультиплексуються на кілька серверних; у цій роботі недоступний на тарифі Burstable, див. вище); (2) маленький пул у коді (`max = 3`); (3) обмеження кількості екземплярів і паралелізму (`maximum_instance_count = 10`, пул 3 з'єднання на екземпляр: найгірший випадок 10 × 3 = 30 з'єднань, менше за ліміт B1ms ~50); (4) пакетна обробка повідомлень; (5) бази, розраховані на serverless (Data API, Aurora Serverless, NoSQL).

## Що сталося на практиці: вичерпання з'єднань

Перший прогін емулятора (25.11.2026, 11:42 UTC, 2 хвилини, ~48 повідомлень/с) ішов із налаштуванням `maximum_instance_count = 20`. Платформа підняла десятки екземплярів функції `process`, кожен відкрив до 3 з'єднань, і PostgreSQL почав відмовляти:

```
Exception: remaining connection slots are reserved for roles with the SUPERUSER attribute
```

За ту хвилину в журналі Application Insights **180 таких помилок**. Жодне вимірювання не загубилось: невдалі повідомлення черга доставила повторно, а ідемпотентний запис не створив дублів (надіслано 5 787, у базі 5 787).

Після зниження `maximum_instance_count` до 10 (найгірше 30 з'єднань) 5-хвилинний прогін (14 606 вимірювань і 20 знімків) пройшов **без жодної помилки з'єднання**. Це і є відповідь на питання, чому кількість з'єднань обмежує serverless-функції: обчислення масштабуються майже миттєво, а база ні.

## Вимірювання під час 5-хвилинного прогону

| Показник | Значення |
|---|---|
| Надіслано емулятором | 14 606 вимірювань + 20 знімків, 0 помилок |
| Записано в базу | 14 606 + 20 (усі) |
| Час обробки одного повідомлення функцією `process` | p50 66 мс, p95 756 мс |
| Від вимірювання до появи в базі | p50 101 мс, p95 4,8 с |
| Позначено аномалій (`sudden_jump`) | temperature 88, humidity 35, light 23 (за обидва прогони) |

План запиту історії підтверджує, що використовується індекс первинного ключа і сортування не потрібне:

```
Limit
  ->  Index Scan Backward using measurements_pkey on measurements
        Index Cond: ((sensor_id = 'temp-kyiv-01') AND (measured_at >= …) AND (measured_at <= …))
```
