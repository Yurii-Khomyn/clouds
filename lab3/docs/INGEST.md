# Приймання даних у чергу

## Схема повідомлення

`POST {INGEST_URL}` із заголовком `x-api-key: <ключ>` і `Content-Type: application/json`.

| Поле | Тип | Опис |
|---|---|---|
| `sensor_id` | рядок, 1–64 символи: літери, цифри, `-`, `_` | Ідентифікатор датчика |
| `sensor_type` | рядок із переліку: `temperature`, `humidity`, `light`, `camera` | Тип датчика (`camera`: бонус 7) |
| `value` | число | Значення вимірювання |
| `unit` | рядок (до 16 символів) | Одиниця виміру (`°C`, `%`, `lx`) |
| `location` | об'єкт `{ "lat": число, "lon": число }` | Координати датчика (-90…90 і -180…180) |
| `measured_at` | рядок ISO 8601 в UTC | Час вимірювання |
| `object_key` | рядок, лише для `camera` | Ключ знімка в Blob Storage (`camera/<sensor_id>/…`), отриманий від `/api/camera/upload-url`; для камери `value` = розмір у байтах, `unit` = `bytes` |

## Відповіді

| Код | Коли | Тіло |
|---|---|---|
| `202 Accepted` | Повідомлення прийнято й покладено в чергу | `{ "message_id": "<sensor_id>|<measured_at>" }` |
| `400 Bad Request` | Не JSON або не пройшла валідація | `{ "error": "<опис помилки>" }` |
| `401 Unauthorized` | Нема ключа або він хибний | `{ "error": "invalid or missing x-api-key" }` |
| `503 Service Unavailable` | Черга тимчасово недоступна | `{ "error": "queue is unavailable, retry later" }` |

`message_id` складається з `sensor_id` і `measured_at`. Те саме значення використовується як `messageId` у Service Bus і як первинний ключ запису в базі, тому повторне надсилання того самого вимірювання не створює дубля.

## Приклад запиту

```bash
curl -i -X POST "$INGEST_URL" \
  -H "x-api-key: $API_KEY" \
  -H "content-type: application/json" \
  -d '{
    "sensor_id": "temp-kyiv-01",
    "sensor_type": "temperature",
    "value": 21.4,
    "unit": "°C",
    "location": { "lat": 50.4501, "lon": 30.5234 },
    "measured_at": "2026-11-25T12:00:00.000Z"
  }'
```

Реальні відповіді розгорнутого приймача (25.11.2026):

```
POST /api/ingest, x-api-key: wrong        -> 401 {"error":"invalid or missing x-api-key"}
POST /api/ingest, value: "x"               -> 400 {"error":"value must be a finite number"}
POST /api/ingest, коректне тіло            -> 202 {"message_id":"smoke-temp|2026-11-25T11:42:03.000Z"}
```

Приклад помилки валідації (`value` не число):

```
HTTP/2 400
{"error":"value must be a finite number"}
```

## Чому приймач не обробляє дані сам, а лише складає в чергу

1. **Швидка відповідь.** Датчик не повинен чекати, поки дані будуть оброблені й записані в базу: приймач відповідає за кілька мілісекунд, бо виконує лише перевірку формату й відправлення повідомлення.
2. **Незалежність від бази.** Якщо база повільна, перевантажена чи недоступна, дані не втрачаються: вони чекають у черзі. Без черги приймач, що пише в базу напряму, почав би повертати помилки, а датчики втрачали б вимірювання.
3. **Згладжування піків.** Емулятор може на мить надіслати у кілька разів більше повідомлень, ніж база встигає записати. Черга приймає пік, а обробка йде у своєму темпі.
4. **Окреме масштабування.** Приймання й обробка масштабуються незалежно, кожна своєю кількістю екземплярів функції.
5. **Повторні спроби без втрати даних.** Повідомлення, яке не вдалося обробити, повертається в чергу, а після кількох невдач потрапляє в чергу недоставлених, а не зникає.
