## Завдання 1. Застосунок у контейнері

### Що зроблено
- **Застосунок** («Все для дому»): Node.js + Express, PostgreSQL. Фронтенд віддається тим самим сервісом.
  - `GET /health`: чи живий процес (до бази не ходить).
  - `GET /products`: каталог із бази.
  - `POST /orders`: створити замовлення. `GET /orders`: останні замовлення.
- **`app/Dockerfile`**: образ застосунку.
- **`compose.yaml`**: застосунок + PostgreSQL, запуск командою `docker compose up -d --build`.

### Як це показати
```bash
cp .env.example .env        # задати POSTGRES_PASSWORD
docker compose up -d --build
open http://localhost:3000
docker compose down         # volume лишається
docker compose up -d        # замовлення на місці
```

### Питання, які можуть поставити

**Чому не `latest`?** Тег `latest` може змінитись між збірками, і те саме `Dockerfile` дасть різний образ. Версія `node:24.21.0-alpine3.24` дає відтворювану збірку.

**Навіщо `package.json` копіюється окремо від коду?** Це окремий шар для `npm ci`. Docker кешує шари: поки залежності не змінились, шар береться з кешу. Код змінюється частіше, тому його копіюємо після залежностей.

**Чому не від root?** Якщо процес зламають, зловмисник отримає права звичайного користувача, а не root у контейнері. Тут `USER node` (uid 1000).

**Що таке `npm ci --omit=dev`?** Установка точно за `package-lock.json` (відтворювано) і без dev-залежностей (менший образ).

**Навіщо `.dockerignore`?** Щоб у образ не потрапляли `node_modules`, `.git` і `.env`. Так образ менший, а секрети не витікають.

**Як дані переживають `docker compose down`?** Дані бази лежать в іменованому volume `db-data`, який живе окремо від контейнера. `down` видаляє контейнери й мережу, але не volume. Лише `down -v` видалить і дані.

**Чому застосунок не стартує раніше за базу?** У `compose.yaml` для `db` є healthcheck (`pg_isready`), а `app` має `depends_on: condition: service_healthy`. Додатково застосунок сам повторює підключення до бази до 30 разів.

**Де пароль до бази?** Тільки у файлі `.env`, який у `.gitignore`. У репозиторії лише `.env.example` із заглушкою. Рядок підключення збирається в `compose.yaml` зі змінної.

**Чому порт бази не опублікований?** У сервісу `db` немає `ports`. База доступна лише всередині мережі compose, ззовні видно тільки застосунок на `3000`.

**Чому ціну беремо з бази, а не від клієнта?** Браузер можна підмінити, тож сума замовлення рахується на сервері за цінами з таблиці `products`.

**Що таке HEALTHCHECK у Dockerfile?** Команда, якою Docker перевіряє, що застосунок відповідає на `/health`. У хмарі цей ендпоінт використає балансувальник.

## Завдання 2. Розгортання в Azure через Terraform

### Що зроблено
Папка `infra/`, провайдер `azurerm`, регіон `switzerlandnorth` (студентська підписка дозволяє лише 5 регіонів).

| Файл | Що описує |
|---|---|
| `versions.tf`, `variables.tf` | провайдери і змінні |
| `network.tf` | VNet, дві підмережі, firewall (NSG) бази, приватна DNS-зона |
| `database.tf` | Azure Database for PostgreSQL Flexible Server 17 (B1ms) |
| `registry.tf` | приватний реєстр ACR, особистість застосунку, роль AcrPull, перша збірка образу |
| `app.tf` | Log Analytics, середовище Container Apps, сам застосунок |
| `budget.tf` | бюджет $20 зі сповіщеннями на email (50/80/100% і прогноз) |

Запуск: `cd infra && cp terraform.tfvars.example terraform.tfvars` (заповнити), далі `terraform init && terraform apply`.
Публічна адреса виводиться в `app_url`. Видалення: `terraform destroy`.

### Питання, які можуть поставити

**Де рядок підключення до бази?** Його збирає Terraform і кладе в секрет Container Apps (`secret`), а в контейнер він потрапляє як змінна середовища `DATABASE_URL`. У репозиторії його немає.

**Звідки пароль до бази?** Його генерує `random_password`. Він зберігається лише в `terraform.tfstate`, а state у `.gitignore`. Тому state не можна втрачати (без нього `destroy` не працює) і не можна публікувати.

**Як застосунок тягне образ із приватного реєстру без пароля?** Admin-користувач ACR вимкнено. Застосунок має user-assigned managed identity з роллю `AcrPull` на реєстр.

**Навіщо `time_sleep` 60 с?** Ролі в Azure застосовуються не миттєво. Без паузи застосунок міг би стартувати раніше, ніж отримає право тягнути образ.

**Як образ потрапляє в реєстр при першому `apply`?** `terraform_data` із `local-exec` збирає образ командою `docker buildx build --platform linux/amd64 --push`. Платформа `amd64` обов'язкова: Mac на Apple Silicon (arm64) збирає образ, який в Azure не запуститься. Надалі образи публікуватиме CI.

**Чому в Terraform `ignore_changes` на образ?** Образ далі оновлює CI. Без цього Terraform відкочував би кожен деплой до початкового тегу.

**Навіщо випадковий суфікс в іменах?** Імена реєстру і Postgres глобально унікальні в усьому Azure.

**Що пішло не так під час розгортання (чесно).**
1. Провайдери ресурсів (`Microsoft.App`, `ContainerRegistry`, `DBforPostgreSQL` та інші) у новій підписці не зареєстровані. Їх реєстрували вручну через `az provider register` (це налаштування підписки, а не ресурс).
2. Один провайдер, `Microsoft.ManagedIdentity`, спершу пропустили. Перший `apply` зупинився з помилкою `MissingSubscriptionRegistration`. Після реєстрації другий запуск докинув лише решту (4 ресурси), решта не пересоздавалась. Це показує, що Terraform ідемпотентний.
3. Azure сам додав до підмережі бази точку `Microsoft.Storage` (для резервних копій), і `plan` показав розбіжність. Її записано в код, щоб Terraform не намагався її прибрати.

**Чому бюджет теж у Terraform?** Методичка вимагає, щоб усе в акаунті було описане в Terraform.

## Завдання 3. Мережева ізоляція

### Що зроблено
- **База** (`database.tf`): `public_network_access_enabled = false`, `delegated_subnet_id` у приватній підмережі `snet-db`. Публічної адреси немає.
- **Firewall (NSG `nsg-db`)** на підмережі бази:
  - пріоритет 100: Allow, TCP 5432, джерело `10.0.2.0/23` (підмережа застосунку);
  - пріоритет 4096: Deny, усе інше.
- **DNS:** приватна зона `homeshop.private.postgres.database.azure.com` прив'язана до VNet, тому ім'я бази резолвиться лише всередині мережі.
- **Застосунок:** назовні лише HTTPS (порт 443). Порт 3000 контейнера не публікується. HTTP без TLS перенаправляє на HTTPS (301).

### Докази (живі команди)
```bash
az postgres flexible-server show -g rg-homeshop -n <сервер> --query network.publicNetworkAccess   # Disabled
az network nsg rule list -g rg-homeshop --nsg-name nsg-db -o table                                 # 2 правила
az network public-ip list -g rg-homeshop                                                            # порожньо
nc -z -w 5 <db_fqdn> 5432                                                                           # ім'я не резолвиться ззовні
curl -I http://<app_url>                                                                            # 301 -> https
```

### Питання, які можуть поставити

**Чому в NSG є явне Deny?** За замовчуванням Azure має правило `AllowVnetInBound`: усі ресурси в одній VNet бачать один одного. Без явного Deny із пріоритетом 4096 до бази мав би доступ будь-хто в мережі. Правила обробляються за зростанням пріоритету, тому Allow (100) спрацьовує раніше за Deny (4096).

**Методичка вимагає «не від IP-діапазонів», а в нас діапазон `10.0.2.0/23`.** Чесна відповідь: у Azure джерелом у правилі NSG може бути Application Security Group (ASG), але ASG призначається мережевому інтерфейсу ВМ. Container Apps не має власного інтерфейсу, у який можна підставити ASG, тому для нього найближчий еквівалент це власна окрема підмережа застосунку. Вона виділена лише під Container Apps, тож «від застосунку» і «від його підмережі» тут практично те саме. Альтернатива з ASG це запуск на віртуальній машині (Virtual Machines дозволені методичкою).

**Чому база взагалі недоступна з інтернету?** Три незалежні бар'єри: (1) немає публічної адреси, (2) NSG забороняє все, крім підмережі застосунку, (3) ім'я бази резолвиться лише через приватну DNS-зону всередині VNet.

**Що таке делегована підмережа?** Підмережа, віддана під конкретний сервіс (тут Postgres). Лише цей сервіс може створювати в ній ресурси.

## Завдання 2. Розгортання в Azure через Terraform

### Що зроблено
Уся інфраструктура описана в `infra/*.tf` і створюється командою `terraform apply`:

| Файл | Ресурси |
|---|---|
| `network.tf` | група ресурсів, VNet, дві підмережі, NSG бази, приватна DNS-зона |
| `database.tf` | Azure Database for PostgreSQL Flexible Server 17 (`B_Standard_B1ms`) і база `shop` |
| `registry.tf` | Azure Container Registry, особистість застосунку, роль `AcrPull`, перша збірка образу |
| `app.tf` | Log Analytics, середовище Container Apps, сам застосунок |
| `budget.tf` | місячний бюджет із сповіщеннями на email |

### Як це показати
```bash
cd infra
cp terraform.tfvars.example terraform.tfvars   # subscription_id, alert_email
terraform init && terraform apply
terraform output app_url                       # публічна адреса
terraform destroy                              # у кінці: прибрати все
```

### Питання, які можуть поставити

**Як рядок підключення потрапляє в застосунок?** Terraform збирає його з адреси сервера та згенерованого пароля й кладе в секрет Container Apps. Контейнер отримує його як змінну `DATABASE_URL`. У репозиторії рядка немає.

**Де пароль до бази?** `random_password` генерує його при `apply`. Він лежить лише в `terraform.tfstate`, який у `.gitignore`.

**Як застосунок тягне образ із приватного реєстру без пароля?** Через керовану особистість (user-assigned managed identity) з роллю `AcrPull`. Admin-користувач реєстру вимкнено.

**Чому образ збирається з `--platform linux/amd64`?** Mac на Apple Silicon збирає `arm64`, а Container Apps працює на `amd64`. Без прапора образ не запуститься.

**Чому `ignore_changes` на образі?** Образ далі оновлює CI, і Terraform не повинен відкочувати його до початкового тегу.

**Чому є `time_sleep` на 60 секунд?** Права `AcrPull` в Azure застосовуються не миттєво. Без паузи застосунок міг би стартувати до того, як отримає право тягнути образ.

**Чому `apply` довелось запускати двічі?** Новій підписці треба «підключити» сервіси (`az provider register`). Я пропустив `Microsoft.ManagedIdentity`, і перший запуск зупинився. Створені до помилки ресурси лишились, і другий запуск докинув решту. Terraform ідемпотентний: він створює лише те, чого бракує.

**Що таке дрейф і що сталось із підмережею?** Azure сам додав до підмережі бази службову точку `Microsoft.Storage`, а Terraform хотів її прибрати. Я записав її в код, щоб код збігався з реальністю.

**Чому регіон `switzerlandnorth`?** Студентська підписка дозволяє лише 5 регіонів (політика Azure). Цей має всі потрібні сервіси.

**Що коштує грошей?** Найбільше база (приблизно 0,4 €/добу), далі реєстр і Container Apps. Тому після захисту обов'язково `terraform destroy`.

## Завдання 3. Мережева ізоляція

### Що зроблено
- База в **приватній підмережі** `snet-db` (`10.0.1.0/24`), делегованій сервісу Postgres. **Публічної адреси немає** (`publicNetworkAccess: Disabled`).
- **Firewall бази (NSG `nsg-db`)**: дозволено лише TCP 5432 з підмережі застосунку `10.0.2.0/23`, решта вхідного трафіку заборонена (`deny-all-inbound`).
- **Приватна DNS-зона**: ім'я сервера резолвиться у приватну адресу лише всередині VNet.
- **Застосунок публікує лише 443**: HTTP на порту 80 переадресовується на HTTPS (301), порт контейнера 3000 назовні закритий.

### Що перевірено в самому Azure
| Перевірка | Результат |
|---|---|
| `publicNetworkAccess` бази | `Disabled` |
| Ім'я бази ззовні | не резолвиться |
| Правило NSG | лише `5432` з `10.0.2.0/23` |
| Порт 3000 ззовні | закритий |
| Порт 5432 ззовні | закритий |
| `http://` | 301 на `https://` |
| Застосунок читає/пише в базу | працює |

### Питання, які можуть поставити

**Чому правило NSG дозволяє підмережу, а не «security group застосунку»?** У методичці написано «не від IP-діапазонів». У Azure правило NSG може посилатись на Application Security Group (ASG), але ASG прив'язується до мережевої картки віртуальної машини. **Container Apps не має мережевої картки, яку можна додати до ASG**, тому найточніше, що дозволяє Azure для Container Apps, це окрема підмережа, виділена лише застосунку. Підмережа `snet-app` призначена тільки для нього, тож правило фактично означає «лише від застосунку». Для ASG довелось би запускати застосунок на віртуальній машині.

**Навіщо правило `deny-all-inbound`?** Без нього діє стандартне правило Azure `AllowVnetInBound`, і будь-який ресурс у VNet міг би стукати в базу. Явна заборона з низьким пріоритетом це закриває.

**Що таке делегована підмережа?** Підмережа, віддана одному сервісу (тут Postgres). У неї можуть розгортатись лише його ресурси.

**Чому не можна було зробити базу публічною, а потім закрити?** В Azure режим мережі Postgres Flexible Server не змінюється після створення. Довелось би знищити й перестворити базу (10–15 хвилин), тому приватну мережу закладено з самого початку.

**Чому порт 3000 назовні закритий, хоч застосунок слухає 3000?** Container Apps сам приймає трафік на 443 і передає його контейнеру на 3000 всередині. Порт 3000 зовні не опубліковано.

## Завдання 4. Load balancer

### Що зроблено (`infra/loadbalancer.tf`, `infra/app.tf`)
- **Azure Application Gateway** (`Standard_v2`) із єдиною публічною адресою в усій інфраструктурі (`pip-homeshop-lb`) і власною підмережею `snet-gateway`.
- Середовище Container Apps **внутрішнє** (`internal_load_balancer_enabled = true`, `public_network_access = "Disabled"`): публічної адреси в застосунку немає, напряму з інтернету до нього не дістатись.
- **Health check:** probe `GET /health`, очікує `200`, інтервал 15 с, поріг 3 невдалі перевірки.
- Бекенд це приватна адреса внутрішнього середовища. Container Apps вибирає застосунок за заголовком `Host`, тому балансувальник підставляє його явно.

### Докази (живі команди)
```bash
curl http://<app_url>/health                     # 200 через балансувальник
curl https://<fqdn застосунку>/health            # не відповідає: напряму недоступний
az network application-gateway show-backend-health -g rg-homeshop -n agw-homeshop   # Healthy
az network public-ip list -g rg-homeshop         # лише pip-homeshop-lb
```

### Питання, які можуть поставити

**Чому балансувальник єдине, що видно з інтернету?** Середовище внутрішнє: воно має лише приватну адресу у VNet. Публічна IP є тільки в Application Gateway.

**Що робить health check?** Балансувальник сам кличе `/health`. Якщо екземпляр тричі не відповів `200`, трафік на нього не надсилається. Ендпоінт навмисно не ходить у базу: він перевіряє, що процес живий.

**Чому адреса `http://`, а не `https://`?** Методичка HTTPS не вимагає. Сертифікат можна додати на listener балансувальника наступним кроком. Трафік усередині VNet між балансувальником і застосунком іде по HTTP.

**Чому Application Gateway, а не простий Azure Load Balancer?** Application Gateway працює на рівні HTTP (L7): розуміє шляхи й заголовки та вміє HTTP health check. Звичайний Load Balancer працює на рівні TCP (L4).

**Скільки це коштує?** Це найдорожчий ресурс (приблизно 5–6 € на добу), тож після захисту обов'язково `terraform destroy`.

### Що пішло не так (чесно)
1. **Заміна середовища на внутрішнє.** Azure не дозволяє перемкнути існуюче середовище на внутрішнє, його довелось знищити й створити наново. На цей час сайт був недоступний.
2. **Нестача потужностей у регіоні.** У `germanywestcentral` створення середовища, підключеного до VNet, стабільно падало з `ManagedEnvironmentCapacityHeavyUsageError` (`AKSCapacityHeavyUsage`), хоча звичайні середовища без мережі там створювались. Було кілька невдалих спроб, після чого всю інфраструктуру перенесли в `switzerlandnorth` (`terraform destroy`, зміна змінної `location`, `terraform apply`). У новому регіоні середовище створилось за 3 хвилини.
3. **Ліміт підписки.** Студентська підписка дозволяє лише одне середовище Container Apps, тому зламана заготовка блокувала нові спроби, і її довелось видаляти вручну.
4. **Затримка узгодженості Azure.** Одразу після створення Azure іноді відповідав `404 ResourceNotFound` про щойно створені ресурси. Повторний `apply` це виправив: Terraform підхоплює рівно те, що лишилось.

**Чому регіон змінювався?** Через нестачу потужностей, а не через помилку в коді. Завдяки тому, що все в Terraform, перенесення зводиться до зміни однієї змінної (`location`).
