# Кешування

## Що закешовано і як

Кеш Redis (контейнер `redis:7-alpine` у тому самому середовищі Container Apps, адреса `ca-homeshop-redis:6379`, доступна лише всередині середовища). Схема cache-aside у `app/src/cache.js`:

1. сервіс шукає ключ у Redis;
2. є в кеші: повертає (заголовок `X-Cache: HIT`);
3. немає: читає з бази, записує в кеш на 45 секунд, повертає (`X-Cache: MISS`).

Закешовано `GET /products`, `GET /products/{id}` і найнавантаженіший за вартістю запит `GET /products/popular` (бестселери: агрегація по всіх позиціях замовлень). Приватні дані (`/me`, `/orders`) не кешуються. Якщо Redis недоступний, сервіс працює напряму з базою.

Захист від лавинного звернення до бази (cache stampede): коли ключ сплив, лише перший запит на екземплярі йде в базу, решта чекають на той самий результат (`inflight` у `cache.js`).

## Порівняння «без кешу / з кешем»

Умови: 60 користувачів, 9,5 хвилин, 2 екземпляри без автомасштабування (щоб масштабування не псувало порівняння), ті самі сценарій і база.

| Показник | Без кешу | З кешем |
|---|---|---|
| p95 латентності, клієнт | 177 мс | 105 мс |
| p50 / p99, клієнт | 62 / 295 мс | 47 / 199 мс |
| Запитів за секунду | 135,7 | 146,5 |
| Час читань каталогу на сервері, p50 / p95 | 16 / 148 мс | 3 / 5 мс |
| CPU бази даних, середнє / максимум | 80 % / 93 % | 52 % / 71 % |
| Частка влучань у кеш | не застосовується | 99,7 % (33 318 влучань, 110 промахів) |

Кеш знімає ~35 % навантаження з бази (80 % → 52 %), p95 для клієнта падає на 41 %.

## Примітка про попередній вимір

Спершу кешувався лише `GET /products` (5 рядків). Прогін дав p95 82 мс без кешу і 89 мс з кешем: запит до 5 рядків за первинним ключем коштує ~2 мс, тож кеш нічого не виграє, а мережа до Швейцарії (~40 мс) затуляє решту. Кеш дає ефект лише на запиті, який справді дорогий, тому додано `/products/popular` з агрегацією.

Обмеження порівняння: кожен прогін додає ~8 000 замовлень, тому агрегація в другому прогоні трохи важча. Прогін без кешу йшов після прогону з кешем, отже його умови трохи гірші. Приріст ~15 % у вартості агрегації на тлі 5-разової різниці часу читань (16 мс проти 3 мс) не змінює висновку.

## Скільки клієнт може бачити застарілі дані

Не більше 45 секунд (TTL). Бестселери після нового замовлення не оновлюються до закінчення TTL; каталог товарів змінюється лише адміністратором напряму в базі.

Як зменшити:
- менший TTL (15 с): частіші промахи, більше навантаження на базу;
- інвалідація: після `COMMIT` у `POST /orders` видаляти ключ `products:popular` (`DEL`), тоді дані застаріють лише на мить. Не реалізовано, бо для бестселерів затримка в 45 с припустима;
- для даних, що змінюються часто, не кешувати.

## Чому не кеш у пам'яті процесу

За кількох екземплярів кожен мав би власну копію: після зміни даних екземпляри віддавали б різні відповіді, а інвалідація одного екземпляра не торкалась би інших. До того ж кожен новий екземпляр стартував би з порожнім кешем і за автомасштабування усі нові екземпляри разом звернулися б до бази. Спільний Redis дає один кеш на всіх.
